# KV cache 接口讨论

状态：设计讨论中，尚未开始实现。当前实现目标是 Qwen3；DeepSeek-V4.1-Flash 只要求在代码设计上保留扩展性。Backend 兼容不在本轮范围。

## 已确定的结构

- 存储父类与存储子类分离；子类申请实际存储，公共请求管理逻辑独立复用，见 ADR 0001。
- 同一请求的各类历史共用块表，见 ADR 0002。
- 历史采用 page_first，窗口与过程状态采用统一状态槽位，见 ADR 0003。
- 整批最大容量预检，运行中按实际计算需求分配编号，见 ADR 0004。

## 已确定的接口选择

初始化接口显式接受历史块大小、块数，以及需要时的状态槽位数；由存储子类计算字节数并申请存储。首版不在缓存模块中根据显存预算自动推算容量。

普通 K/V 与 V4.1 使用不同的层缓存视图数据类。视图引用预分配存储，不单独申请缓存；公共请求管理逻辑不解释视图字段。父类统一取层接口，具体类型可通过泛型表达。示例类名和字段名仍待最终整理。

请求自己持有缓存分配对象，其中包含块表和可选状态槽位编号。公共管理器不维护 request_id 到分配对象的请求表；分配对象在扩容和释放时由调用者传入。分配对象的具体类型和方法签名尚待最终确认。

分配或扩容失败时，已有分配保持不变，本次临时取得的编号全部归还。实际计算开始后若失败，不尝试回滚窗口或压缩过程状态；确认无在途访问后，释放该请求的全部缓存。容量足够不代表对应位置的 KV 已有效。

状态槽位复用时不重新初始化，公共管理器不调用状态初始化钩子。计算路径负责在读取前覆盖需要使用的内容，并通过正确的有效范围避免读取旧请求数据；不能假定预分配或复用的存储自动为零。

已计算 token 数等有效进度由请求维护。缓存分配对象只保存编号与分配生命周期信息，缓存模块不提供 reservation/commit 接口。压缩器本身必要的算法状态仍属于缓存存储。

## 接口草案（待整体确认）

- `BaseKVCache[LayerViewT]`：报告 `block_size`、`num_blocks`、`num_state_slots`；提供 `layer(layer_id)`。无额外状态时 `num_state_slots` 为零。具体子类申请存储。
- `Qwen3KVCache`：普通 K/V 的 page_first 存储，返回 `KVLayerView`。
- `DeepSeekV41KVCache`：后续扩展位置，返回 `V41LayerView`；当前不实现。
- `CacheAllocation`：由请求持有的 `block_ids`、可选 `state_id` 及所属管理器、释放状态等生命周期元数据。调用者通过管理器改变分配，不能自行修改块归属。
- `CacheManager(storage)`：组合块编号分配器及需要时的状态编号分配器，不维护请求表。
- `check_capacity(max_lengths)`：在整批开始前预检保守最大容量，失败报错，不分配编号。
- `allocate(num_tokens)`：返回分配对象，同时申请需要的状态槽位；失败不泄漏编号。
- `ensure_capacity(allocation, num_tokens)`：仅扩容，目标表示需要容纳的 token 总数；不缩容、不更新有效进度。
- `free(allocation)`：确认无在途访问后归还编号并标记已释放；不释放大 buffer、不清零存储。

首版无跨请求前缀共享；编号的重复释放、跨管理器误用及非法长度应明确报错。GPU 执行顺序由调用者保证，缓存模块不负责异步任务跟踪。
